# Миссия 4 — Мост к трекеру команды

ROLE: project
GOAL: Ученик умеет проводить данные через мост между инструментами: CSV-экспорт из трекера команды → его `tasks.json` (с маппингом статусов) → доска и отчёт; и обратно — из отчёта в короткое сообщение для чата руководителю.
WHY: Команда живёт в своём трекере — Jira, Trello, Asana, YouGile, Bitrix24 или Excel-табличке техлида — и никто не будет вести твой `tasks.json` руками. Контур из миссий 1–3 полезен ровно настолько, насколько дёшево в него попадают свежие данные. Файл-экспорт раз в неделю — самый дешёвый мост: ноль согласований с ИТ, ноль доступов, а 80% пользы уже есть. Это тот же навык, которым проджект склеивает выгрузку из CRM с таблицей финансов.

## Наставнику (как вести — читает Claude Code)

- НЕ лекция. Сначала спроси: в чём живёт его команда и может ли он прямо сейчас достать оттуда выгрузку. У большинства трекеров экспорт в CSV или Excel есть в настройках проекта или доски — пусть поищет; не находит за пару минут — не залипаем, идём по учебному пути (шаг 1, вариант Б).
- Скажи оценку времени: 30–45 минут.
- Дай сделать РУКАМИ:
  1. **Достать экспорт.** Вариант А (лучший): реальная выгрузка из трекера команды → положить в `sandbox/pm/integration/export.csv` (если выгрузка в Excel `.xlsx` — пусть агент сохранит копию как `export.csv`; читает он оба, но проверка ждёт именно .csv). Сразу предупреди про гигиену: если в выгрузке чувствительное (зарплаты, персональные данные клиентов) — пусть попросит агента вычистить лишние колонки первым же шагом. Вариант Б: реального экспорта нет → пусть попросит агента сгенерировать учебный `export.csv` в формате типичной выгрузки Trello или Jira — колонки на английском, статусы называются иначе (`In Progress`, `Blocked`, `Done`), даты в другом формате, 5–8 задач по теме его проекта. Принципиально: формат НЕ должен совпадать с его схемой — вся миссия про конвертацию.
  2. **Импортировать с маппингом.** Сначала страховка: пусть попросит агента закоммитить `sandbox/pm/tracker` (точка возврата перед импортом — git из фундамента). Затем пусть попросит агента: сопоставь колонки экспорта с полями `tasks.json`, покажи таблицу соответствия статусов (`In Progress` → `doing` и т.п.) и список того, что добавится/обновится — ДО записи. Ученик проверяет маппинг глазами (это решение проджекта, не агента: куда падает их шестой статус, которого у него нет?), потом даёт добро. Согласованный маппинг — записать разделом «Маппинг статусов» в `sandbox/pm/tracker/STATUS-RULES.md`, чтобы следующий импорт шёл по нему.
  3. **Прогнать через контур.** Пересобрать доску и отчёт — задачи из экспорта должны доехать до `board.html` и `report.md`. Момент истины миссии: данные из чужого инструмента проехали весь его конвейер.
  4. **Обратный мост.** Пусть попросит агента собрать из `report.md` короткую версию для мессенджера — `sandbox/pm/report/for-chat.txt`: 5–7 строк, светофор словом, два-три главных факта, риски одной строкой. То, что реально вставляется в чат руководителю без редактуры.
- Точки помощи: перед импортом страшно сломать `tasks.json` → правильный инстинкт, git из фундамента: пусть попросит агента закоммитить `sandbox/pm/tracker` до импорта — будет точка возврата; кракозябры в русских названиях задач → классика выгрузок, пусть покажет агенту кусок файла — тот определит кодировку и переконвертирует; в экспорте статусов больше, чем у него → решение принимает ученик как PM (что считать `doing`, что `blocked`), агент только фиксирует; задачи задвоились после импорта → спросить агента, по какому полю он сличал задачи, и договориться о ключе (id из трекера или точное название).
- Назови типичное заблуждение вслух: «интеграция — это API и нужен программист». API — лишь один из мостов, и часто самый дорогой (доступы, согласования, поддержка). Файл-экспорт раз в неделю руками — тоже интеграция, работает с первого дня (атом `.course/knowledge/project/02-data-bridges.md`).
- В конце — вызови проверку и, если passed, похвали конкретно: контур замкнулся — данные команды сами доезжают до его доски и отчёта, а отчёт сам сжимается в сообщение для чата. Это уже не упражнение, это рабочий инструмент. Открой финальный проект.

## Ученику (живой сценарий)

«Представь: контур из прошлых миссий работает, но задачи-то живут в трекере команды. Вручную перепечатывать их в свой tasks.json — значит завести второй трекер и умереть от рассинхрона недели через две. Сегодня строим мост: выгрузка из их трекера заезжает в твой контур одной просьбой.» (~30–45 минут)

Что делаем руками:

1. Достань выгрузку из трекера команды (CSV или Excel — ищи экспорт в настройках проекта/доски) и положи в `sandbox/pm/integration/export.csv`. Не достаётся — попроси агента сделать учебный экспорт «как из Trello»: чужие колонки, чужие статусы, чужой формат дат. Чувствительные колонки — вычисти сразу.
2. Сначала застрахуйся: попроси агента закоммитить папку `sandbox/pm/tracker` — точка возврата перед импортом.
3. Попроси агента импортировать экспорт в `tasks.json`: пусть покажет маппинг колонок и статусов и что изменится — ДО записи. Проверь маппинг сам: куда падает их «In Review», если у тебя такого статуса нет, — это твоё решение. Согласованный маппинг пусть запишет в `STATUS-RULES.md`.
4. Пересобери доску и отчёт. Найди на доске задачу, которая приехала из экспорта, — мост работает.
5. Обратный путь: попроси собрать из отчёта `sandbox/pm/report/for-chat.txt` — 5–7 строк для мессенджера: светофор, главное, риски. Прочитай: вставил бы ты это в чат руководителю без правок? Нет — правь формулировки, это твой голос.

К концу данные ходят в обе стороны: из трекера команды — в твой контур, из контура — в чат руководителю.

## Артефакт

`sandbox/pm/integration/export.csv` (реальная или учебная выгрузка в «чужом» формате), обновлённый `sandbox/pm/tracker/tasks.json` с задачами из экспорта, раздел «Маппинг статусов» в `STATUS-RULES.md` и `sandbox/pm/report/for-chat.txt` — версия отчёта для мессенджера.
